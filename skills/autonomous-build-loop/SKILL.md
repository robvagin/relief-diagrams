# Autonomous Build Loop — метод долгого билда без потери темпа

Суть метода одним абзацем: **состояние проекта живёт в файлах, а не в чате; исполнение идёт автономной
очередью с гейтами; человек принимает результат глазом по артефактам (скриншоты, пуши), а не читает
отчёты.** Мерило прогресса — коммиты и кадры, не документы. Этот метод дал на реальном проекте больше
за одну ночь автономной очереди, чем за три недели «эстафеты» (бриф → человек-курьер → сессия → отчёт).

## 1. Луп-файл — единственный носитель состояния

Вся работа = ОДИН markdown-файл-очередь (шаблон: `assets/LOOP_TEMPLATE.md`). Правила:

- Пункт очереди — хирургический: что сделать, где именно (файл:строка/сим), референс (кадр/спека), DoD.
  Не «улучшить меню», а «кнопка ··· (index.html:251) сейчас работает как back (:2160) — сделать X».
- Исполнитель после каждого зелёного пункта: атомарный коммит → пуш → **галочка [x] + хэш ПРЯМО В ФАЙЛЕ**.
  Файл переживает обрыв сессии; новая сессия читает файл и продолжает — контекст чата не нужен.
- Человеку — галерея скриншотов до/после (`~/Desktop/<проект>-loop/`), не тексты. Одна вставка в
  терминал запускает всё: «Читай <файл>, исполняй очередь сверху вниз, автономно».
- Ревьюер (плановая сессия) пополняет очередь новыми пунктами и НЕ плодит промежуточных документов.
  Если план не влезает в пункт очереди — это спека (см. §3), и она пишется только когда без неё нельзя.

Почему это работает: чат суммируется и врёт, файл — нет; галочка с хэшем — это и статус, и аудит-трейл.

## 2. Шаг 0 — снапшот реальности до кода

Перед любой интеграцией с внешними данными (API, логи, форматы файлов): сначала снять РЕАЛЬНЫЕ образцы
в fixtures (обезличив чувствительное), сверить план с фактом, расхождения записать в README рядом с
fixtures — и только потом писать код. На четырёх коннекторах подряд реальность опровергала план каждый
раз (несуществующие поля, «ошибка вместо ответа», состояния, которых не бывает). Час шага 0 экономит
день отладки и, главное, не даёт коду закрепить неверную модель мира.

## 3. Спека-до-кода — только для рискованных пассов

Не для всего (это душит темп), а когда правка касается ядра/данных/денег: сначала короткая спека +
детерминированные тест-вектора (golden-файлы), вектора зелёные на чистом модуле — потом врезка в
рантайм. Форма: чистая функция вход→выход, никакого DOM/глобального состояния — тогда вектора гоняются
где угодно. Визуальная полировка спеки не требует — ей хватает референс-кадра и DoD в пункте очереди.

## 4. Байт-гарантии — валюта смелости

Большой рефакторинг безопасен только если безопасность ДОКАЗУЕМА, а не «мы аккуратно»:

- Перенос кода — байт-в-байт, дифф старого и нового обязан показывать только заранее объявленные строки.
- Поведенческий эталон: golden-trace (числа кадров/координат, округлённые + хэши строк рендера),
  закоммиченный как бейзлайн; «дифф пуст» = поведение не тронуто. Пиксельные бейзлайны — вторым слоем.
- Совместимость смысла: «новый путь на старом входе даёт байт-идентичный старый выход» — как вектор.
  (Пример: fixture на офсетах, материализованная на замороженных часах, deep-equal со старым литералом.)

С такими контрактами страшные правки (де-монолит, смена шелла, оконный рендер) идут быстро: красный
дифф мгновенно показывает, ЧТО поехало, и «revert, вторая попытка» дешевле осторожности.

## 5. Честные стопы — автономия без самодеятельности

Автономный исполнитель обязан знать, где остановиться, иначе автономия опаснее эстафеты:

- Жёсткий список «не трогать» в шапке луп-файла (ядро-геометрия, калибровки, токены, приватность).
- Гейт красный дважды на одном пункте → [skip] + лог, дальше по очереди. Не «дожимать».
- «Не уверен → не меняй, запиши в needs-human» — и продолжай. Пункт, требующий вкуса/глаза, помечается
  заранее и не исполняется вслепую.
- Пункт ждёт спеку → НЕ импровизировать, взять следующий. (Запрет пишется прямо в пункте.)
- Дерево чистым между пунктами: коммит или revert, никогда «грязное на потом».

## 6. Privacy by construction

Чувствительные данные не должны попадать в выход ПО ПОСТРОЕНИЮ кода, а не по внимательности ревью:
наружу выходят только счётчики/enum'ы/метаданные; секреты живут в gitignored-конфиге/Keychain, код
берёт их по ссылке; и это запинено grep-векторами («выход не содержит ни одной строки исходного
текста», «в фиде нет token/authorization»). Вектор дешевле инцидента.

## 7. Гигиена долгого проекта (мелочи, которые копятся в недели)

- **Канон-файл без секции «текущее состояние»** — она врёт через день; состояние живёт в git/очереди.
- Один писатель на горячий файл; ревьюер читает `git show <ref>:<file>`, НЕ переключает ветки в чужом
  рабочем дереве (checkout ревьюера + живой git исполнителя = битый index.lock).
- Каждый новый визуальный эффект — за флагом с ручкой отключения (`?feature=off`): дёшево, спасает
  отладку и вкусовые споры.
- Фоновые демоны перечитывают конфиг на цикле (или это записано как правило «правил конфиг — рестарт»).
- Когда человек начинает пересылать сообщения между сессиями — это сигнал сменить процесс на луп (§1),
  а не ускоряться внутри старого.

## Как применять этот скилл

1. Новый проект/этап → создать луп-файл из `assets/LOOP_TEMPLATE.md`, наполнить хирургическими пунктами.
2. Интеграция с внешним миром → потребовать шаг 0 (§2). Рискованное ядро → спека+вектора (§3).
   Рефакторинг → байт-гарантии (§4).
3. В шапку лупа — границы и стопы (§5), приватность — векторами (§6).
4. Напоминать человеку его роль: глаз по галерее + решения по помеченным пунктам. Всё остальное — очередь.


## Перенято из obra/superpowers v6.1.1 (сверка первоисточника 2026-07-13) — 4 приёма, каркас наш

Проверено против README v6.1.1 (246k★). Их методология = чистый SDLC (brainstorm → worktree → план
2-5-мин задач → subagent-driven → TDD → review). Наш луп сильнее в визуальном контексте (галерея для
глаза, байт-гарантии, privacy-векторы, needs-human стопы). Перенимаем четыре недостающих приёма:

1. **Свежий сабагент на пункт (опция для длинных очередей).** Одна долгая сессия-исполнитель гниёт
   контекстом к утру. Режим: оркестратор держит ТОЛЬКО луп-файл, каждый пункт исполняет свежий
   сабагент; оркестратор принимает по гейтам. Когда: очереди >10 пунктов / ночные прогоны.
2. **Двухступенчатое ревью пункта:** сначала соответствие ПУНКТУ (сделано ровно то, что написано),
   потом качество кода. Одна ступень пропускает «сделал хорошо, но не то».
3. **Галочка только с уликой.** [x] ставится с ПРИЛОЖЕННОЙ строкой вывода гейта (вставить последнюю
   строку прогона в луп-файл рядом с хэшем), не «прогнал, зелено» на словах. Evidence over claims.
4. **Красная фаза вектора.** Golden/тест-вектор обязан СНАЧАЛА провалиться (доказать, что умеет
   ловить поломку) и только потом зеленеть. Вектор, родившийся зелёным, ничего не охраняет.
   Плюс: для репо-проектов рискованные наряды — в git worktree, не в живом дереве (.bak — фолбэк
   для не-репо).
